# cc-cursor-kit 项目总结

更新：2026-09-04

## 一句话

用 **Claude Code 当壳与工具执行器**，推理与账单走 **Cursor 订阅**（默认 `grok-4.6`），不另付 Anthropic。对用户：**除模型不同外，功能体验对齐标准 Claude Code**。

仓库仍无首次 commit；实现已收敛为单路径 `adapter/`。（注：此后已建立 git 基线并推送 GitHub）

## 目标与边界

| 做 | 不做 |
|----|------|
| Anthropic Messages ↔ Cursor SDK 长会话 | Keychain / 仿客户端 |
| `customTools` 结构化 tool_use，会合回 CC 本地执行 | 未文档化 Connect / Bidi |
| `/compact`、工作区、Skills/Agent 目录尽量对齐 | 复活 `proxy/` 文本 JSON 桥 |
| 只绑 `127.0.0.1`，`.env` 不进 git | 截断 CC 本地 transcript 压 context% |

账单：Dashboard User API Key → Cursor **Pro+ Included**。依赖：`cursor-sdk>=1.0.30`。

## 演进复盘

1. **早期 `proxy/`**  
   每轮 fork `agent --mode ask`，用文本 JSON 仿真 tool_use。慢、易错、难续聊，与「标准 CC 工具环」不对齐。

2. **判定**  
   双轨（proxy + adapter）对称加功能不可持续；官方可行路径是 Cursor SDK + `customTools`。

3. **现状（2026-09-04）**  
   唯一实现：`adapter/server.py`（约 1300 行）。`proxy/`、`bin/proxy-*`、`bin/login` 已删。研究对照留在 `docs/research/对照.md`。

4. **对齐工作（相对「砍上下文」旧策略）**  
   - system **保留** Skills / Agent 目录（超限分预算压缩，禁止整段砍）  
   - Glob/Grep：CC 已下发 → 会合；未下发 → 本地补缺（workspace 狱）  
   - compact 只认末条 CC 指令；有 pending 不 compact；独立无工具 Agent；缺标签时 adapter 包 `<summary>`  
   - compact / drain **不占** session 大锁  
   - Agent 泄漏 / `turn_id` 串台 / workspace 变更重启 / 烟测隔离 `:4012` 已修  
   - 首轮与 Agent 重建：多带近 10–12 轮历史，减少工具集变化导致的上游失忆

## 架构

```
目标项目目录
  └─ bin/cc
       ├─ 写 runtime/workspace = cwd
       ├─ 起 adapter :4011（双 fork + setsid）
       └─ 启动 Claude Code（profile → ANTHROPIC_BASE_URL）

Claude Code
  GET  /health · /v1/models
  POST /v1/messages · /v1/messages/count_tokens
adapter
  Session(key=CC-Session-Id:Agent-Id)
  Agent.create(disallowed_tools=内置, custom_tools=CC工具[+本地Glob/Grep])
  send → SSE 回灌 Anthropic 事件
  tool_use → execute 阻塞 → CC 执行 → tool_result 会合
Cursor Router（grok-4.6 / haiku→grok-4.5）
```

职责切分：

- **CC**：UI、权限、本地工具、完整 transcript、斜杠命令壳
- **adapter**：协议翻译、瘦身送给 SDK、会话会合、本地补缺只读搜索
- **Cursor**：模型推理与计费

请求状态机（短锁决策，长活动出锁）：

| action | 条件 | 行为 |
|--------|------|------|
| compact | 无 pending 且末条是 CC compact 指令 | 独立无工具 Agent，纯文本 `<analysis>` + `<summary>` |
| drain | 新 user 轮，或 tool_result 已喂中 | 收 worker 事件 → SSE / JSON |
| reemit | 有 pending，本轮不是 tool_result | 不放弃，原样再吐 tool_use |
| stale | 声称 tool_result 但 id 对不上 | 回 `Acknowledged.` |

`count_tokens` 走本地估算（汉字偏高、略保守），促 CC 更早 compact；不是上游真 token。

## 能力对齐现状

| 能力 | 状态 |
|------|------|
| Read / Write / Edit / Bash / Web* / 会话 | 对齐（经会合；工具字段有 path/file_path 等别名） |
| Skill / Agent 子代理 | 工具在 + 目录保留；质量随模型 |
| `/compact` | 可用；坏会话需 `/clear` 或 `/new`；空文本轮回 `OK.` 避免 CC 解析失败 |
| Glob / Grep | 有能力；本地补缺时无 CC 工具时间线；越出 workspace 拒绝 |
| 模型别名 | Claude 系 id 落到 grok；`composer-2.5` 等 Cursor id 直通 |
| 权限交互 | 默认 `bypassPermissions`（`CCA_PERMISSION_MODE=manual` 可改） |
| 视觉 / prompt cache / 真 token | 缺口（图片块 omitted 占位） |

## 使用与运维

```bash
./bin/setup                    # 一次；若无 venv，adapter-start 会自动调
# 编辑 .env → CURSOR_API_KEY
cd /path/to/your-project && /path/to/cc-cursor-kit/bin/cc

./bin/status
./bin/adapter-stop             # 改完 server.py 后需重启才吃到新代码

./scripts/test-compact-detect.sh   # 不耗 API：摘要检测 / pending 阻断 / 模型别名 / workspace 狱
./scripts/smoke-all.sh             # qa / read / write-edit / glob-grep；独立 :4012，不杀日常 :4011
```

改代码后旧 adapter 进程不会热更新：先 `adapter-stop` 再 `bin/cc`。  
`bin/cc --proxy` 已拒绝。workspace 变更时 `adapter-start` 会自动停旧起新。

调试：`CCA_DUMP_REQUESTS=1` 把请求摘要追加写到 `runtime/adapter-requests.jsonl`。

## 关键环境变量

见 `.env.example`。常用：`CCA_SYSTEM_MAX`、`CCA_TOOL_DESC_MAX`、`CCA_TOOL_RESULT_MAX`、`CCA_PROMPT_MSG_MAX`、`CCA_CONTEXT_HINT`（可置空）、`CCA_PERMISSION_MODE`、`CCA_SONNET_MODEL` / `CCA_HAIKU_MODEL`、`CCA_SESSION_TTL`、`CCA_RUNTIME` / `CCA_ADAPTER_PORT`（烟测隔离用）。

## 2026-09-04 两轮效率攻坚（13 commits）

**性能**（实测 grok-4.6）：

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 同 session 第 2 轮首 token | 13.7s | 1.4s（增量发送） |
| 首个真实请求首 token | 7.4s | 2.8s（prewarm send） |
| 长任务端到端（真实 CC） | 6 分钟+ | 32s |
| composer-2.5 冷启动 | — | 1.5s（≈增量） |

**能力对齐标准 CC**：

- **图片桥**：CC image block → SDK `UserMessage.images`（此前误判为文本桥缺口）。小图/大图（1.4MB 截图）/多图/多轮引用（checkpoint 保留图片）/图片+工具混合全部实测通过
- **ESC 中断**：客户端断开 → `run.cancel()` 取消上游（`status=cancelled`），不再白烧额度；on_idle ping 断开异常改为传播（思考期 ESC 也能检测）
- **`--continue/--resume` 修复**：`has_tool_result_turn` 原扫全历史，恢复会话时旧 tool_result 误判 stale 回 "Acknowledged."；改为只看末条 user 消息
- **子代理**：Agent 工具落独立 session（`sid:aid` key），实测正确
- **多 tool_use 并发会合**：一轮 2 个 tool_use 闭环 `fed=2`，无死锁
- **compact 端到端**：`kind=compaction` 正确识别，`<analysis>+<summary>` 双块协议完整
- **并行工具引导**：CONTEXT_HINT 加并行指导，实测一轮 2 个独立 Read
- **日志截断**：adapter.log 超 10MB 启动时截断保留尾部 2MB

**硬缺口（实测确认无解）**：

- **15M 假窗口**：CC 2.1.260 对 unknown model 硬编码 `<total_tokens>15000000</total_tokens>`，`AUTO_COMPACT_WINDOW` 等环境变量均无效 → auto-compact 永不触发，**靠手动 /compact**
- 流式中等粒度（上游 ~16 字符/delta，adapter 链路零缓冲，Cursor bridge 推送粒度限制）

## 2026-09-04 第三轮：鲁棒性与真实场景验收

**测试基建（3 个新脚本）**：

- `test-edge-cases.sh`：异常矩阵 9/9——畸形 JSON→400、空 messages→200、200KB 消息→200、数字 content→200、并发写同文件双 session 不挂死、未知路径→404
- `perf-baseline.sh`：延迟回归门禁（短问答 4.1s / 工具轮 6.1s / 增量 2.8s，阈值内）
- `bin/bench` 基线注释补上游长尾观测（grok 偶发 25-125s，adapter 无法干预）

**场景验收（真实 CC）**：

- 50 轮长会话压力：均值 4.0s 无衰减，40 轮告警正确触发
- NotebookEdit：.ipynb 精确改写 ✓（CC 27 件工具至此全覆盖）
- CLAUDE.md 自动加载：有/无目录对照验证 ✓（system 实测 6873 字符，占 SYSTEM_MAX 57%）
- 大文件精确 Edit：500 行制度文档改第 250 行，其他行零改动 ✓
- 制度分析 demo：读考勤办法→引 Q/XXJH 基准→体例+缺失审查→写意见，125s 专业级产出
- 长文流式：6381 字中文细则，四章齐全结尾完整，4225 deltas 无截断
- TTL 过期恢复：session 过期 drop → 续聊自动重建（create 12ms）+ 全量重放正确回忆

**修正的认知与配置**：

- 增量发送省的是延迟不是 token：上游 usage 按全量上下文计（9505→10113 缓增），compact 既防溢出也控成本
- haiku 别名路由修复：会话残留的 `CCA_*_MODEL` 环境覆盖导致走 grok-4.6；grok-4.5 实测已可用（区域问题消失），干净环境路由正确；故障排查补「查 `env | grep CCA_`」
- prewarm send 换 composer-2.5（预热效果验证为模型无关，用最快模型）

**防线新增**：system core 超预算时打 WARNING 日志（CLAUDE.md/用户规则不被静默截断）。

## 结论

主路径可用，红线清楚。与标准 CC 的差距集中在「模型换成 Grok」的能力差，以及文本桥 / 无 cache 等架构取舍。  
产品口径不变：**瘦身可以，砍能力目录不行**。
