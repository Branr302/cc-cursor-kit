# 对照开源吸收笔记

更新：2026-09-03  
原则：上游只走官方 **Cursor SDK**。不接未文档化 Connect。  
本 kit：**仅 adapter**；`proxy/`（agent ask 文本桥）已废弃删除。

## 本 kit

```
Claude Code
  → 127.0.0.1:4011 /v1/messages
  → Cursor SDK Agent + customTools（完整 input_schema）
  → 结构化 tool_use；会合回 CC 本地执行
  → 真 SSE
```

- 鉴权：`CURSOR_API_KEY`
- 默认模型：`grok-4.6`
- 启动：`bin/cc`

## 为何去掉 proxy

- 每轮 fork `agent`、文本 JSON 仿真 tool_use → 慢、易错、难续聊  
- 与 adapter 双轨对称加功能不可持续  
- SDK customTools 已覆盖「CC 执行工具、Cursor 只推理」的合同

## 对照表

- **[starhunt/star-cliproxy](https://github.com/starhunt/star-cliproxy)** — cli subprocess 形态；本 kit 早期 proxy 近此，现已用 SDK 取代。  
- **[BerriAI/litellm](https://github.com/BerriAI/litellm)** — Messages/SSE/`count_tokens` 形状可借；快靠现成推理 HTTP。  
- **[raine/claude-code-proxy](https://github.com/raine/claude-code-proxy)** — 只吸收公开开关；**不实现** Connect/Bidi。  
- **[musistudio/claude-code-router](https://github.com/musistudio/claude-code-router)** — 分流叙事。  
- **[HosheaLi/dsv4-cc-proxy](https://github.com/HosheaLi/dsv4-cc-proxy)** — SSE 清洗；上游官方 HTTP ≠ SDK。

## 明确不做

私有接口、双执行器、复活 proxy、截断 CC 本地对话压 context%。

## 2026-09-04 实测调研新增（cursor-sdk==1.0.30 / CC 2.1.260）

- **SDK 多模态**：`UserMessage(text, images)` 原生支持 base64 图片（`types.py` 的 `SDKImage`/`_image_to_proto_wire`），「文本桥」判断过时——图片桥已落地
- **SDK 取消**：`Run.cancel()` / `Agent.cancel_run(run_id)` 存在且生效（ESC 中断链路依赖）
- **SDK 流式粒度**：on_delta 逐 event 直调无批处理，~16 字符/delta 是 Cursor 上游 bridge 推送粒度
- **CC unknown model 窗口**：硬编码 `<total_tokens>15000000</total_tokens>`，`CLAUDE_CODE_AUTO_COMPACT_WINDOW` / `CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT` 均不改变 → auto-compact 永不触发
- **CC 工具协议**：一轮多 tool_use 并发执行、同一条 user 消息回全部 tool_result；`X-Claude-Code-Agent-Id` 区分子代理
- **CC `--continue`**：恢复会话历史含旧 tool_result，adapter 判定结果轮必须只看末条 user 消息
- **prompt 大小与首 token 无关**：40KB 仅 +0.2s；冷启动瓶颈是上游会话建立固定开销 2-3s
- **增量发送的收益边界**：省的是传输/解析（首 token 13.7s→1.4s 实测），**不是 token**——上游 usage 显示增量轮 input_tokens 仍按全量上下文计（9505→10113 缓增）。长会话成本随轮数线性增长，手动 /compact 既防溢出也控成本
